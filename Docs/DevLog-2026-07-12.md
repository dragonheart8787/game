## Patch 7:能力融合(核心架構驗證)

### 目標

驗證 Ability Graph 系統本身撐不撐得住「兩個能力組合成第三個」——不是
複製貼上 Slash 和 Bind 的參數兜一個新能力,而是系統性的組合。

### 技術選型(兩個候選,選了合併函式)

- ❌ 方案 2「手組 DA_Ability_RendLock、抄 Slash/Bind 的節點值」:DataAsset
  存的是值的**副本**,改 DA_Ability_Slash 的傷害,RendLock 不會跟著變。
  這只證明結構欄位夠用,證明不了「組合」。
- ✅ 方案 1「`FuseAbilityGraphDefs()` 合併函式」:RendLock 在 BeginPlay
  從**當下已註冊的** Slash/Bind 定義(不論來源是 DataAsset 還是 C++ 預設)
  推導出來。改 Slash 的 DataAsset → RendLock 自動跟著變,零 RendLock 側
  改動。整個 RendLock **沒有任何手寫數值**,連 cooldown/energy 都是推導的。

### 融合規則(`UNovaAbilityFusionLibrary::FuseAbilityGraphDefs(Primary, Secondary, Id, Name)`)

| 欄位 | 規則 |
|---|---|
| Shape / Path / DefaultParams | 取 Primary(delivery 由主能力定義;runtime param 繼承行為原樣保留) |
| Spawn / Constraint | Primary 非 None 則取 Primary,否則取 Secondary(空槽填補) |
| Affect | 兩者的 affect 鏈**串接**(Primary 先) |
| EnergyCost | Primary + Secondary(融合技付兩份代價) |
| CooldownSeconds | max(Primary, Secondary)(至少跟最重的部件一樣重) |

實際結果:`RendLock = Cone(Slash) + Instant + [Damage 20 → Slow 50%/3s] +
TetherToActor(3s)`,cost 25 = 10+15,cd 2.0 = max(0.8, 2.0)。

### 架構發現(誠實回報)

1. **暴露的真實限制**:`FNovaAbilityGraphDef` 原本只有**單一** `Affect`
   欄位,表達不了「Damage+Slow 疊加」。這正是融合第一個踩到的架構天花板
   ——單槽節點結構天生不利於效果疊加類的組合。
2. **修法(本次)**:加 `TArray<FNovaAbilityAffectNode> ExtraAffects`
   (附加式欄位,既有 DA_Ability_Slash/Edgewall 序列化完全不受影響),
   `ExecuteAffect` 改為對每個命中目標跑整條 affect 鏈;單一 affect 的
   既有能力行為逐位元不變(Slash/Edgewall/Bind 迴歸邏輯不動)。
3. **殘留的設計債(下次融合類 patch 要面對)**:
   - `Affect + ExtraAffects` 是過渡形態;乾淨形態是單一 `TArray Affects`,
     但那需要處理既有 DataAsset 的遷移(CoreRedirects 或一次性重存資產)。
     本次刻意不做,避免動到已驗證資產。
   - Spawn/Constraint 仍是**單槽**:Sculpt×Bind→Cage 若要「牆 + 鎖鏈」
     同時存在就會踩到 Spawn 單槽;三重融合 Prism Weave 大概率需要
     Constraint 也鏈化。同樣的 ExtraXxx 手法可以直接套用。
   - 融合觸發仍是顯式註冊(BeginPlay 內 Slash+Bind → RendLock),真正的
     「玩家在空間中把兩個能力捏在一起」的輸入層/圖層融合是之後的事;
     本次驗證的是資料與 runtime 層的組合能力,這一層是通的。

### 結論:**系統撐得住**。合併函式 60 行、runtime 改動一處、零新節點
型別,就組出第三個能力且全部行為可迴歸驗證——組合能力是架構本身的
性質,不是為 RendLock 特製的。

## PIE 迴歸:NovaFusionTestDriver(16/16 全綠,首跑即過)

方法沿用 Bind driver pattern(MCP 記憶體內生成、不存關卡、
`StartPIE(WarmupSeconds:0)` → StopPIE → 讀 log),時序沿用「改狀態→驗證
留 ≥1.5s」的教訓。**所有期望值都在 runtime 從已註冊的 Slash/Bind 定義
推導**(GetAbilityDefinition),測試本身不含任何寫死的調校數值——這使
「融合跟隨部件」也被測試結構本身證明。

- composition@0.5:三定義齊、shape+path 繼承自 Slash、affect 鏈 =
  Slash.Damage(20)+Bind.Slow(0.5x/3s)、constraint 繼承自 Bind、
  cost 25==10+15、cd 2.0==max(0.8,2.0) ✅×5
- cast@1.0:首發成功、同幀重施放被自身 cd 擋(2.0s)、能量 100→75(−25)、
  **Slash/Bind 冷卻保持 0**(融合不污染部件) ✅×4
- verify-hit@1.5:血 100→80(恰 = Slash 傷害)、速 300→150(恰 = Bind 倍率)、
  tether 錨定 dummy ✅×3
- move@2.0 → verify-follow@3.5:tether 跟隨移動後 dummy,**drift 0.00cm** ✅
- verify-restore@5.0:速度復原 300、tether 依時釋放 ✅×2
- independence@5.5:Slash 施放只持有自己的 cd;Bind 施放後 RendLock 仍
  ready;**Slash 與 Bind 同時在冷卻中 RendLock 照樣施放成功**(決定性
  判別:融合技冷卻完全獨立) ✅×3

附帶取得的部件實際數值(來自 DataAsset):Slash dmg 20 / cost 10 /
cd 0.8;Bind slow 50%/3s / cost 15 / cd 2.0。

不動 IMC/BP 資產、不佔 CastAbility1/2。
